# 维护与分发

本仓库是插件规则和模板的唯一维护源。使用方的项目文档由使用方维护。

## 源码边界

- 可安装内容全部位于 `plugins/document-first-development/`。
- 运行时相对引用保持在插件内；仓库 README、维护说明及验证材料不作为技能运行依赖。
- 项目任务不得回写插件或安装缓存。通用改进应成为单独授权的维护任务。
- 样例只使用重新构造的通用场景，不引述真实项目、代码、组织、个人路径或日志。
- 不为方便维护新增强制 MCP、shell、专属 API 或其他技能依赖。

## 修改规则

先在 [插件设计基线](design.md) 中明确影响权威、授权、门禁或状态的改变，再修改规则和相关模板。入口保持简短，详细内容按需加载；不要在多个文件独立维护同一长规则。

新增模板字段前检查其职责：主契约不定义验收要求，非目标只能记录开发者明确提出或明确批准的内容；Progress/Issues 不得出现设计定义、方案或设计说明；提案必须非生效，确认后归并主契约。具体项目策略不能上升为所有项目的默认要求。

## 检查

维护者可使用 Python 3.10+ 标准库运行：

```text
python scripts/validate_package.py
python scripts/validate_package.py --self-test
```

Python 只用于维护检查，不是使用技能的依赖。检查 JSON、技能入口、相对引用及包路径；语义与客户端行为应结合独立构造的场景验证，不能用结构检查代替行为或客户端验收。

验证时区分结构检查、独立行为演练、CLI 安装/发现、桌面交互和实际模型执行，并注明实际版本、执行范围和限制。

## 版本与发布

仓库采用 MIT License；仓库根目录与插件目录中的许可证保持一致，使安装包携带相同许可说明。

包版本在插件清单中维护。改变规则语义时说明兼容影响；仅修文字或链接也应让使用方能识别获取的版本。

发布前确认仓库地址、发布者信息、许可证选择、版本/ref 以及验证范围。只填写真实信息，不放置看似可用的假地址。发布、推送、安装到既有环境均需要相应授权。

不在本维护说明中维护实际发布状态或验收结果；发布与验收结论应以实际执行证据为依据。
