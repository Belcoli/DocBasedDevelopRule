# 验证、状态与可观测性

按 [核心规则 R6](rules.md#r6--状态证据与验收) 记录真实证据。主契约定义设计行为，不定义验收要求；本文件提供验证与记录方法。

## 验收约定与设计

验收要求在主契约之外按项目既有方式或本次明确沟通约定，不强制新增文档。区分被验证的设计与如何判断接受：前者引用主契约，后者引用适用约定或说明其确认来源；实际执行、覆盖范围及结果记录于 Progress。

在既有授权和项目策略内选择相称的常规验证，不自行新增用户验收门槛。关键验收要求未明确且影响结论时，只澄清相关部分；验收反馈若要求改变行为，按设计变更更新主契约，不能把验收标准直接当作设计定义。

## 各类证据分别表达

| 方式 | 通常可支持的结论 | 不能自动扩大的结论 |
|---|---|---|
| 静态检查 | 文件结构、引用、局部逻辑或配置符合所检查条件 | 真实运行行为成立 |
| 编译 | 本次配置和依赖下的编译结果 | 全环境可运行、零警告或业务正确 |
| 自动测试 | 用例在指定环境和夹具中通过 | 未覆盖分支、真实外部服务或完整运行链正确 |
| 实际运行日志 | 本轮观测到的事件、状态及链路 | 未记录部分未发生、画面正常、所有路径正确 |
| 人工观察 | 明确场景下看见或操作确认的现象 | 未观察内部状态、所有极端情况均正确 |
| 用户验收 | 用户对明确对象、版本和范围的接受 | 未提及部分、未来版本或完整 QA 全部通过 |

自动测试可以在真实运行环境执行，也可以是隔离模型。记录其环境和替代依赖；“自动”不是证据强弱等级。不同证据可组合支持一项结论，但不能混写成一次未实际执行的验证。

## 最小记录与按需补充

普通任务至少记录对象/契约条款引用、实际验证方式、结果及覆盖边界。需要复现、跨主机或高风险判断时，再补日期、实现/契约基线、环境、命令或操作、证据位置、重要输入、观察样本和限制。按用途提供足够信息，不为小任务填满无关栏目。

证据链接指向实际资料；被覆盖、缺失或临时保存时标明可用性。历史验证报告可以保留其当时结论，不能声称原始资料仍存在或本轮已经复跑。

## 多维状态

在 Progress 分开记录：

- 实现状态：待开始、进行中、已实现等项目选定词汇。
- 每种适用验证：未执行、通过、失败、部分覆盖或不适用，并给出范围。
- 验收：未请求、待验收、指定范围已接受等项目选定词汇。
- 关联问题：只有 Issue 编号或链接，问题与决策状态由 Issues 管理。

“已实现”不等于“全部验收通过”。不需要的验证标记不适用并简述依据；依据是风险和约定要求，而非为了关闭任务临时降低标准。证据缺失且不构成门禁时可继续无关开发；确实阻断当前工作时关联适用 Issue。

## 变更与历史

按变更影响定位需要重新验证的条款、实现基线和证据。保留旧通过记录及其日期；新增独立记录，不把旧结果改写为未曾通过，也不把旧结果套用到新行为。未受影响部分可引用旧基线，不无故重开整个阶段。

日志缺失时先核对观测点、级别、过滤、采样、运行标识及文件是否完整，再判断证据能支持什么。无法判断则记录“证据不足”，不写成“行为未发生”。

## 可观测性计划

需要运行验证时提前选择必要的观测方式。只有涉及正式功能、接口、状态或副作用的设计变化才归入主契约；测试步骤、验收标准、采样与证据要求在项目验证约定中处理，不写入主契约。验证操作可按项目需要另存测试说明，不强制创建提案、证据附件或验证报告；实际方法与结果仍记录于 Progress。

临时诊断应能关联一次运行、相关对象、输入、关键分支、状态变化和输出；按问题选择必要信息，避免不受控高频输出。临时日志保持只读，测试输入独立标识其副作用，删除条件可追踪。

具体日志 API、编译条件、文件组织及清理工具由项目适配。正式诊断不因删除临时探针被误删；删除探针后正式行为应仍独立成立。

## 工具不可用

能执行什么就明确执行并记录什么。无法编译、运行、访问服务或获取人工验收时，仍可完成已授权的调查、文档或静态检查；保留尚缺证据及适用门禁。

需要用户运行时提供最小操作和预期观察项的契约引用。不得伪称读取了内存、控制台或外部服务；不得自动安装额外工具或把某个专属工具写成通用前提。
