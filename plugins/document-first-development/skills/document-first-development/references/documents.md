# 文档职责与维护

本文件规定文档分工，不定义任何项目设计。权威边界见 [核心规则 R1](rules.md#r1--设计只有一个权威归属)。

## 归属表

| 文档角色 | 维护什么 | 不维护什么 |
|---|---|---|
| 需求 | 目标、用户需求、约束、输入来源、范围 | 类型、接口、组件职责或具体实现设计 |
| 里程碑 | 交付范围、拆分、依赖顺序、验收目标引用 | 实际完成状态、设计定义、Issue 讨论 |
| 主契约（可一份或多份） | 各自覆盖范围内的当前有效设计定义 | 验收要求、验证步骤、证据要求、执行进度、未决讨论、互相冲突的旧规则 |
| Progress | 实际执行状态、验证方法/结果/范围及证据引用 | 设计说明、接口定义、候选/最终解决方案、Issue 内容 |
| Issues | 未决问题、影响、分级、局部门禁、所需决策及关闭证据要求 | 设计定义、替代方案、执行进度或完整验证结果 |
| 开发规范/项目适配 | 工作方式、职责映射的入口、责任/验证/归档策略 | 项目功能设计或对主契约的覆盖 |

### 可选辅助材料

以下角色只约束项目选择保存的材料，不要求项目创建对应文档、占位文件或索引。方案可在对话中讨论，调查与审核可以直接反馈；必要确认依据可在主契约中简短说明，验证方法与结果仍由 Progress 记录。没有这些辅助文档不是接入缺项或推进门禁。

| 可选角色 | 选择保存时维护什么 | 不维护什么 |
|---|---|---|
| 设计提案 | 明确非生效的方案讨论与待确认变化 | 当前设计权威或实施授权 |
| 历史/决策记录 | 确认来源、日期、替代关系、原因和修订链接 | 第二份当前有效设计 |
| 调查/审核/证据附件 | 有来源的观察、推断、证据及其适用基线 | 当前完成度、未决问题清单或有效设计定义 |

归属按内容而非文件名决定。已有体系可以保留原名称和目录；若一篇文件承担多个角色，应至少有明确分区和唯一引用位置。**Progress 与 Issues 保持独立文档，不混写。** 不把主契约的设计定义分散到这些文档的附件。

## 文档入口

项目文档入口只保存职责到文件的映射、模块主契约索引、项目适配及确已保存的辅助材料入口。不写“当前完成了什么”或“下一步被什么阻断”的副本，链接到对应权威记录。

项目可以有一份或多份主契约，每份明确覆盖范围。尽量避免多个契约覆盖同一模块或重复描述同一内容；确需涉及同一模块时，区分各自负责的边界。每个设计条款只在一份契约中定义，共用边界指定权威归属，其他契约引用。主契约之间不得冲突；发现冲突须在相关实施前统一修订，不得按文件新旧或标题层级自行择一。

## 主契约的适当粒度

根据实际模块记录必要的设计内容：职责与边界、文件/组件组织、接口签名及行为、输入输出、错误与副作用、状态与数据流、所有权与生命周期、不变量。栏目按实际设计使用，不要求将全部私有方法纳入接口清单；对已经记录的接口，按下述粒度说明内部逻辑、状态/数据流及入参与内部变量的生命周期。

非目标不作为必需栏目。仅在开发者明确强调该条目的非目标，或明确批准/赞同建议时记录；未获此类明确认可时省略，不自行推测、扩写或将缺失视为设计不完整。

主契约不定义验收要求、验收标准、验证步骤或证据要求。验收在主契约之外按项目既有方式或本次明确沟通约定；保存位置由项目选择，不强制新增文档。里程碑可引用项目已约定的验收目标，Progress 记录实际验证与验收结果，Issues 记录适用的未决问题与门禁。验收约定和这些记录都不能替代设计定义；涉及行为变化时先更新主契约。

### 接口条目的说明粒度

主契约中记录的每个接口都应说明以下三组内容，不能只列签名，也不能由模块级总述替代：

1. **调用约定**：明确名称/完整签名，输入与输出的类型、含义和约束，前置与后置条件，错误处理及副作用。没有输出、错误或副作用时可简明说明。
2. **内部简要逻辑、状态与数据流**：按执行顺序说明主路径、关键分支及必要的内部调用；描述读取什么、如何处理、改变哪些状态、写入或返回什么，以及分支和错误如何影响流程。保持设计层面的简要说明，不逐行复制实现。
3. **入参及内部变量的生命周期**：说明各自来源或创建时点、所有者与持有方式、使用范围与读写变化、失效或释放时点，以及调用结束后是否仍被持有。区分变量作用域、所指对象的存续时间与资源释放责任；涉及借用、复制、所有权转移、异步捕获、缓存或跨调用保留时明确说明。退出、异常或取消路径按实际设计说明清理责任。

生命周期相同的变量可以按名称或角色分组说明，明确覆盖对象；不同生命周期不得含混合并。尚无实现时说明已确认的变量角色与预期生命周期，不虚构实现变量名或把未知的持有/释放语义写成事实。

模块级状态和共用数据只在其权威位置定义，接口条目引用它并说明本接口的读取、变化与持有关系，避免重复定义。

## 状态文档如何避免设计泄漏

Progress 的对象写任务/条款编号，设计依据用链接；描述做过的动作、覆盖范围和实际结果。日志或测试观察作为带基线的事实证据，不写成规范性规则，也不整段复制接口语义。

Issues 可以描述观察到的异常、未知项和受影响对象，并链接证据及契约；“待决定什么”用问题表述。候选方案、接口草案及拟议行为在对话中讨论，或按项目需要另存非生效提案；Issue 不收纳这些设计内容，仅在材料已存在时按需链接。已经确定的最终设计进入主契约，不能保留在 Issue 里等待别人推断它是否生效。

## 生命周期

- **新需求**：保留需求输入，识别受影响契约；必要时建立 Issue，是否另存非生效提案由项目选择。
- **确认设计**：更新相关主契约的当前正文及修订标识，检查各契约一致；已有提案标记已合并或按约定归档，指向契约，不补建提案。
- **执行工作**：只在 Progress 更新实现及证据；门禁仍由 Issues 表达。
- **关闭问题**：涉及设计的决定归入契约，其他决定按项目约定处理；实际执行与验收证据在 Progress 记录后，移除或归档 Issue。
- **新增变更**：保留先前基线，重新打开受影响范围；计划只在范围/依赖变化时更新。
- **历史材料**：项目选择保存时标明日期、基线和非现行地位，优先保留原因与链接，避免复制当前规则。

主契约应能识别哪些条款已获认可及其范围；必要确认依据可就地简短注明，或引用已有资料。无需另建历史/决策文档、逐轮记录讨论或单独编写调查/审核报告；不要求 Git 或其他特定工具。
