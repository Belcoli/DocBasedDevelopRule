# 核心规则

这些规则约束开发过程。项目设计由项目主契约定义；文档分工详见 [文档职责](documents.md)，证据记录详见 [验证与状态](verification.md)。

## R1 · 设计只有一个权威归属

主契约是项目一切有效设计的唯一权威说明，可以是一份，也可以按职责维护多份；“唯一”约束设计归属，不约束文件数量。各契约明确覆盖范围，尽量不覆盖相同模块或重复描述相同内容；涉及同一模块时明确不同的职责边界。每条设计只能有一个权威归属，共用设计以引用关联，主契约之间不得存在内容冲突。不得为了形式强行合并或拆分。

Progress、Issues、计划、操作说明、审核结论及聊天摘要均不能定义、解释或覆盖有效设计。尤其 Progress 和 Issues 不写设计说明、接口签名、行为定义、候选方案或已决定的解决方案。它们只引用对应契约条款；需要关联讨论时可引用已有非生效提案，不为补链接强制新建文件。

主契约只维护设计，不定义验收要求、验收标准、验证步骤或证据要求；验收在主契约之外按项目既有方式或本次明确沟通约定，不强制新增文档。验收约定不得取代设计定义，需要改变行为时仍须更新主契约。

需求规定目标和约束，是设计输入；需求变化需要进入契约变更流程。项目适配记录只规定工作方式，不存放功能设计，也不能放宽本插件的权威与授权边界。

## R2 · 先理解，再设计

先阅读相关需求、契约与现有实现；新项目只调查确有关系的技术条件。确认事实、推断与未知项，不用命名或目录猜测行为。

非目标不是主契约的必填内容。只有开发者明确强调某条目的非目标，或明确批准/赞同建议的非目标时，才记录。不得从未提及、未实现、沉默或对其他条款的认可推测非目标；未获明确认可时省略，不为了补齐栏目创建限制或索取确认。

重要未知项包括会改变职责、接口、行为、成本、风险或验收结论的内容。提出聚焦问题或安排调查，不把假设写入生效主契约。普通实施细节在确认范围内合理选择，无需把每个细节升级为决策。

未确认设计可以直接在对话中讨论；项目选择保存提案时须明确标注“非生效”。提案、历史/决策记录、调查/审核/证据附件均为可选材料，不要求创建文档，也不因缺少这些文档阻断工作。获确认内容必须归并对应主契约；提案本身不是实施依据。已有有效契约保持可读，不能用待确认全文覆盖它。

## R3 · 确认、授权与实施

确认设计与授权实施是两项判断。用户明确要求“按此方案实现”可以同时满足二者；单纯讨论或要求调查、解释、审核不授权实施，也不自动授权文档写入。

已确认且已授权范围内的实施、必要验证和相关记录维护不必反复批准。新增范围、重要语义、接口或职责变化先说明影响并更新约定。不能借调查或小修复顺带改公共组件、安装工具、修改插件或整理无关内容。

是否属于小任务由变更的语义与风险决定，不以行数或文件数决定。契约内缺陷修复不需要新建里程碑或重新确认未变化的设计。

## R4 · 当前设计与变更

用户后续明确确认的新决策指导有效契约修订。识别被替代条款及相关模块，在实施前同步主契约；更新当前正文并核对相关契约，保留必要的确认与替代依据；可在主契约内简短注明，已有历史资料按需引用，不要求另建决策或历史文件。不让新旧规则并存或多份契约相互冲突。

确认记录应使下一次对话能够识别已批准的条款与范围。聊天可作为批准来源，但有效设计必须在主契约中自足，不要求重读聊天才能理解。

源码证明实际实现，主契约定义获准设计。遇到不一致，先识别是实现缺陷、未同步的已确认变更，还是尚未批准的偏离；不得自动把代码写回契约当作正确设计。无法判定时仅暂停受影响实施，记录或报告问题；根据本次授权决定是否写入 Issues。

文案修正且不改变设计含义时，按文档编辑授权处理，不重新走功能审批。

## R5 · Issue 门禁

| 分级 | 推进语义 |
|---|---|
| P0 / BLOCKER | 阻止当前约定推进范围内的后续实施；允许调查、决策及已获授权的解阻修复 |
| P1 / REQUIRED | 只阻止明确依赖它的工作；无关开发可继续 |
| P2 / DEFERRED | 在已批准的安全占位或替代边界内继续；进入指定接入、实施或验收阶段前必须处理 |
| P3 / NOTE | 观察、优化或低风险清理；不构成功能阻断 |

每项必须说明影响对象、受阻工作或阶段、所需决策/证据及关闭要求。P0 的“当前范围”须明确，不能扩展到无关项目；P1 不能只写“高优先级”却不标依赖。P2 的占位设计位于主契约，Issue 只引用其边界和到期门禁。

开始相关工作前检查适用门禁；影响范围变化时重新检查。既不能把所有未知项当全局阻塞，也不能用一句 TODO 放行明确阻断项。普通未执行验证可在 Progress 记录，不必全部立为 Issue；当它构成未决问题或依赖门禁时才关联 Issue。

Issue 限制是否可推进，不赋予任何设计定义权。解决后有效设计在主契约、实际结果在 Progress，Issue 从当前未决清单移除或按项目策略归档。归档只保留问题历史和解决记录链接，不成为现行设计副本。

## R6 · 状态、证据与验收

分别表达实现、各类验证和未决问题。一个对象可同时已实现、运行待验证并关联待业务决策的 Issue；不强迫用一个互斥标签表示全部状态。

只记录实际执行和真实证据。静态检查、编译、自动测试、运行日志、人工观察、用户验收不能互相替代。没有日志之前先核实观测覆盖，不直接断言行为未发生。

完成结论限定交付对象、设计基线及项目另行约定的验收范围；契约条款说明被验证的设计，不定义验收门槛。开发与 QA 分工由项目明确，不默认把全部 QA 阻断开发，也不跳过已经约定的必要验收。

保留历史通过及其基线；新增变更只重开受影响部分。证据文件失效只改变可追溯/可复现条件，不抹去真实历史；不得冒称本轮重新执行。

## R7 · 可观测性

需要运行验收的功能提前考虑如何关联输入、关键决策、状态变化和输出。采用项目可用的日志、测试、观测或人工方法，不强制工具或日志 API。

临时诊断与正式行为分离，明确范围及删除条件，不能形成正式行为依赖。日志不能伪装成改变状态的测试输入；需要测试输入时单独识别其副作用及授权。

持久诊断与临时探针区分管理。清理要求写入适用项目约定；清理工作与结果由项目自己的 Issue/Progress 跟踪，不能进入插件实例数据。

## R8 · 接入与交接

先识别现有职责映射，再补缺；不默认覆盖、搬迁或重建。文档入口能定位当前主契约、真实进度和未决问题，项目 AI 指引能定位文档入口。

按本次任务读取相关模块，不要求每轮全量重读。交接记录只提供入口、工作范围和引用，不维护第二套状态或设计。

收尾对照授权范围、最新明确决策、主契约、实际实现、Progress 与 Issues。发现缺口不等于获准扩展修改；只读审核报告差异即可。

## R9 · 插件与项目隔离

插件维护的是通用规则、流程和模板。项目主契约、Progress、Issues、需求、决策、代码、日志、人员及根目录属于项目，保存于项目自己选定的位置。

项目任务不得把实例填入插件模板、修改插件安装缓存或回写通用规则。需要使用模板时复制到已确认的项目文档位置。升级插件也不自动重写项目文档。

独立授权的插件维护可以改进方法，但应先抽象问题并构造通用案例；不得收录实际项目引述、标识、路径或数据。特定技术、组织分工和工具选型只能由使用方项目约定。
