# 开发与需求变更

依据 [核心规则](../references/rules.md)。验证和状态写法见 [验证指引](../references/verification.md)。

## 选取本次最小流程

| 情况 | 处理 |
|---|---|
| 调查、解释或咨询 | 读取所需依据并报告事实、推断及未知；不自动修改 |
| 契约内已授权修复 | 核对相关条款和 Issue 门禁，按既定设计修复，进行相称验证 |
| 文案/格式等低影响修改 | 按授权编辑相关内容，不创建整套开发记录 |
| 新功能或重要设计变化 | 理解需求和实现，讨论方案，确认并更新主契约后实施 |
| 跨模块或依赖变更 | 确认职责归属、接口及影响范围，统一修改相关契约 |
| 只有新设计确认，尚无实施授权 | 在授权范围同步契约；实施保持未开始，不能自行推进 |

## 契约内实施

读取本次目标条款及相关依赖，检查适用门禁。确认代码、配置与现有契约的差异；不要只看状态文档推导应有行为。

明确本次对象和验证范围后实施，保留用户已有改动。需要偏离接口、职责、状态或重要行为时回到设计变更，不先改后补。

验证后把实际实施和证据写入 Progress；问题放 Issues 并链接，设计只在主契约。失败、部分覆盖和未执行分别记录，不能因实施结束就标整个功能验收通过。

## 设计变更

1. 识别需求来源和获准目标，找到设计归属条款。非目标仅在开发者明确提出或明确批准建议时记录；没有明确认可时省略，不根据未提及的内容推测。
2. 调查会改变结论的现有实现与依赖。事实和推断分开，不把未知设计塞入生效契约。
3. 用对话比较有意义的方案；项目选择保存时可用 [非生效提案模板](../assets/templates/design-proposal.md)，无需为讨论新建文件。Issues 只记录待决问题与门禁，可链接已有提案，不收纳设计方案。
4. 明确文件/组件职责；对每个记录的接口，按 [接口说明粒度](../references/documents.md#接口条目的说明粒度) 说明名称/签名、输入输出、前后条件、错误与副作用，内部简要逻辑、状态与数据流，以及入参与内部变量的生命周期。内容可简洁，不能只以模块总述替代。验收要求及验证安排按项目既有方式另行处理，不写入主契约。
5. 根据用户确认更新对应主契约的当前正文与必要确认依据，核对各相关契约不存在冲突或重复定义。已有提案按约定标记归并或归档；无需补建提案或历史文档。
6. 判断是否已有实施授权。若已有则直接实施；若只有设计确认则不推断实施许可。
7. 计划仅在交付范围或依赖变化时更新，Progress 记录执行事实，Issues 按门禁处理。

用户后续提出明确的新决策时，先把受影响的有效契约同步为新约定。已清楚确认的内容不再重复询问；不清楚的关键语义只问真正影响实施的部分。

## 不一致处理

- **实现偏离有效契约**：在已授权修复范围内按契约纠正；重大偏离或原因不明时先调查并限制受影响工作。
- **已确认新决策未同步**：保留确认依据，更新主契约后实施；不能以旧契约反对该新决策。
- **契约之间冲突**：不自行择一实施，确定唯一归属并统一修订，门禁只影响相关工作。
- **Progress/Issues 写了新设计**：这些文字不具有设计效力。只读任务报告；获文档修改授权后移出设计内容：已确认内容归主契约，未确认内容回到讨论；项目选择留存时另存非生效材料，并按需保留历史依据。
- **调查发现范围外缺陷**：报告影响或按授权登记 Issue，不顺带实施。

## 收尾

核对本次修改与有效条款、用户最新明确决策一致；验证范围符合项目适用约定，适用门禁未被绕过。检查主契约未混入验收要求，非目标有开发者明确提出或批准的依据。必要的临时诊断清理按项目要求记录。

最终回答说明实际交付、验证及限制，给出对应文档引用。未变化的主契约无需为增加一条“已完成”而修改；不把执行历史搬进设计正文。
