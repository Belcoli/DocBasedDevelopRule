# 审核与交接

本流程按 [核心规则](../references/rules.md) 执行。审核、交接及整理摘要本身不授权修订代码或文档。

## 一致性审核

先限定模块、时间/版本范围和是否允许修订。按需对照：

1. 最新明确用户决策及其确认来源；
2. 相关主契约的覆盖范围、当前正文、条款归属与修订标识，检查是否重复定义、相互冲突、混入验收要求或自行添加未经明确认可的非目标；
3. 实际实现与相关配置；
4. Progress 的实现和各类验证结论，以及主契约之外适用的验收约定及确认来源；
5. Issues 的未决事项、影响和门禁；
6. 计划中的范围与依赖，以及有关历史材料。

对主契约已记录的每个接口，按 [接口说明粒度](../references/documents.md#接口条目的说明粒度) 检查调用约定、内部简要逻辑与状态/数据流、入参及内部变量生命周期是否清楚且一致；检查接口返回、异步完成或异常退出后的持有和释放关系。

逐项分类：事实不明、设计冲突、已确认变更未同步、实现偏离、状态失真、证据不足或文档职责混写。报告文件/条款、证据、影响范围和需要的下一步授权，不只输出“文档陈旧”。

调查和审核可以直接在对话中反馈，不要求另建报告或证据附件。项目选择保存报告时可以引用有来源的事实，但不能变成第二份设计、进度或 Issue 总表。若获修订授权，分别更新各自归属文档；否则只给发现与建议，不实施“顺手修复”。

## 新对话接手

从项目采用声明进入文档入口，定位：

- 本次目标和修改授权范围；
- 相关模块的有效主契约及必要上位边界；
- Progress 中对应工作项、基线和验证覆盖；
- Issues 中适用门禁；
- 确有需要的需求、计划、设计提案或源码入口。

本轮没有足够上下文时先读取缺失依据，而不是要求用户复述全部历史。发现关键文档缺失或矛盾，只问影响本次工作的部分，同时可以继续不依赖该答案的已授权工作。

## 交接信息的最小形式

记录文档入口、本次工作项/模块编号、相关契约条款、Progress 与 Issues 链接、下一次建议读取的位置，以及临时资料可用性。交接不重写设计和状态，也不要求固定的交接文件；已有入口足够时直接使用。

确需持久交接说明时先确认写入位置及授权，保持它是导航。下一步建议不等于已经获得实施许可。

## 证据与变更复核

区分历史通过、本轮新增结果和未执行项。日志不完整时不从缺失推断行为不存在；隔离模型通过不覆盖真实环境未测行为。

已通过部分只在有新变更或新缺陷影响时重新打开；重新打开的对象和范围记入 Progress，未决问题及其门禁留在 Issues。

## 插件独立性复核

项目事实保留在项目侧。不得把交接、审核、项目自学习或“长期记住”的请求自动解释成修改插件；若用户明确要求改进插件方法，先独立抽象规则，使用通用样例，避免复制项目内容。
