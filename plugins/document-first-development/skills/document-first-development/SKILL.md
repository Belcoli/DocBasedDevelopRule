# 文档先行开发

为项目提供开发 guideline、流程与方法论。具体项目的设计和记录始终由项目自行维护。

## 本次任务先判断

1. 确认用户请求是接入、调查/解释、设计、实施、审核还是交接，以及允许修改的对象。安装插件不等于所有项目已接入，采用流程不等于授权本次实施。
2. 已接入项目先读项目 AI 指引中的采用声明、文档入口和本次相关模块；定位当前主契约、Progress 与适用 Issue。不要每轮全量重读。
3. 本次会话首次使用或规则版本变化时读 [核心规则](references/rules.md)；只读当前任务所需的后续指引。上下文仍可靠时复用已读规则，变更过的文件按需重读。

## 始终保留的边界

- **主契约独占一切有效设计。** 可有一份或多份，覆盖范围清楚、尽量不重复；同一设计只有一个权威归属，契约之间不得冲突。 Progress 和 Issues 不写设计说明、接口定义、候选方案或设计结论，只通过编号和链接引用契约。Issue 可以阻断实施，不能改变主契约。
- 先理解需求与已有实现。重要未知项不得写成确认结论；未确认方案可在对话中讨论，确认后归并主契约。提案、历史/决策记录、调查/审核/证据附件均可选，不要求另行落文档。
- 契约确认与实施授权分别判断；已确认且已授权的范围内不重复索取批准。调查、解释、审核和交接不自动授权修改。
- 主契约只维护设计，不定义验收要求；验收按项目另行约定，实际结果记录于 Progress。非目标仅在开发者明确提出或明确批准时记录，不自行推测或补齐。
- 门禁按影响范围执行；证据按实际方式和覆盖范围表述；历史验收与增量验证分开。
- **项目资料留在项目侧。** 不把项目契约、进度、Issue、代码、日志、主机路径或真实案例写回插件。普通项目任务不授权修改插件。
- 插件只提供行为指引；工具缺失时说明能完成什么、欠缺何种证据，不伪造执行，也不为此自动安装工具。

## 按需阅读

| 场景 | 读取 |
|---|---|
| 新项目初始化、已有项目接入或迁移 | [接入指引](workflows/onboarding.md)；需要映射职责时读 [文档职责](references/documents.md) |
| 新功能、契约内修复、需求变更或实现偏离 | [开发与变更](workflows/development.md) |
| 验证方式、证据不足、多维状态或诊断设计 | [验证与状态](references/verification.md) |
| 只读审核、一致性复核、新对话接手 | [审核与交接](workflows/review-handoff.md) |
| 需要新建或补齐文档 | 先检查既有文档，再选 [模板](assets/templates/README.md)；不批量生成空文件 |

文档改动也遵循授权与职责；计划、状态或报告中的文字不能成为绕过主契约的新设计。

## 结束时

按本次范围报告实际交付、采用的契约依据、验证结果和仍适用的门禁。只在已授权范围内修订项目文档；只读任务报告发现即可。任务规模小时保持输出简短。
